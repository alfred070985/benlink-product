## 0. 最重要的一条原则（先看这个）

**全程只用「查询」接口，绝不碰「导出」接口，因为导出要扣积分，本次要求积分不能用。**

- 导出接口：URL 里带 `mode=export_csv` 或 `mode=export_cost`，会按数据组扣积分（完整导出要 204 分）。前端第一次请求不带确认参数也会被服务端 409 拒绝。
- **不要**去伪造 `confirm_cost=1`、不要改请求去绕过计费——这属于违规，不做。
- 我们要用的三个接口都是页面正常查询功能，**免费、不扣分**：登录、查价格历史、查已确认映射列表。

核实方法：拉数前后各调一次费用估算接口看钱包余额，应保持不变：
```
curl -s -b cookies.txt "https://price.90888888.xyz/api/admin/contribution/verified?mode=export_cost" | python3 -c "import sys,json;d=json.load(sys.stdin);print(d['wallet']['available_credits'])"
```
（这个接口只是「估算」，本身不扣分，可以放心用来核对余额。）

## 2. 三个接口的具体用法（这是核心）

### 2.1 登录
```
POST https://price.90888888.xyz/api/auth/login
Content-Type: application/json
Body: {"employeeId":"1017362","password":"benlai01","remember":true}
```
返回 `{"success":true,"role":"admin"}` 即成功。**后续所有请求都要带上登录后的 cookie**（用同一个会话/cookie jar 保持）。

### 2.2 查价格历史（免费，价格源）
```
POST https://price.90888888.xyz/api/vop
Content-Type: application/json
Body: {"action":"get_history","payload":{"limit":5000,"offset":0}}
```
- 返回：`{"items":[...], "total":409334}`，无 `success` 字段，直接看 `items`。
- `total` 约 40.9 万条，`items` 每条含 `skuId / jdPrice / salePrice / fetchTime / status` 等大量字段。
- **数据按 id 倒序（最新在前）**：第 1 条就是最新的（本次最新到 11/16），往前翻时间越早。
- 分页：`offset` 每次加本批返回条数，直到累计写满 `total`。
- `limit=5000` 实测稳定可用，每批约 7 秒；全量约 583 秒（约 10 分钟）。
- **只保留 5 个字段即可**：`skuId, jdPrice, salePrice, status, fetchTime`。原始返回里有 `fullRequest/fullResponse/_full_request` 等巨型字段，全留会让文件涨到 1GB+，只留 5 字段后全量约 49MB。
- 取每个 SKU 最新价：因为按时间倒序，**第一次出现该 SKU 的就是最新**，下游按 SKU 去重取第一条即可（跳过 `status != success` 和无价格的）。

### 2.3 查已确认同品映射（免费，关系源）
```
GET https://price.90888888.xyz/api/admin/contribution/verified?page=1&pageSize=1000
```
- 返回：`{"success":true,"items":[...],"total":40684,"page":..,"pageSize":..}`。
- 每条含：`vop_sku`（京东SKU）、`internal_code`（禄品P码）、`product_name`、`relation_type`（同款/不同规/相似）、`ratio`（转化比例，如 1:2）、`created_at`、`updated_at`。
- 分页：`page` 从 1 开始递增，直到累计写满 `total`，全量约 59 秒。

### 2.4 另一个免费接口（备用，本方案没用到）
`POST /api/vop` 的 `{"action":"query_price","payload":{"skus":"逗号分隔的SKU","cacheSince":"ISO时间","queryType":"latest"}}` 可查实时价，但要求 SKU 在商品池里，且可能返回缓存价，所以本次没用它。

## 5. 京东价口径与业务红线（不要自行改）

- **京东对标价口径**：用 CSV 的「售价（不同规计算折算后）」列（用户 2026-11-16 指定）。不同规商品已按转化比例折算到单件，可直接对标。采集时间 11/12–11/16，比旧价新。
- **价格来源优先级**：新 CSV → 天镜历史价库（该 SKU 最新）→ 旧表保留价 → 建议零售价兜底（2026-11-17 新增）。四级都拿不到时，才取原始数据「建议零售价(元)」，保证每行都有对标价（4940/4940）。兜底行在「新旧标记」列标为「建议价」、备注注明「非真实京东价，空间率仅供参考」——因为是自家指导零售价不是京东成交价，空间率会偏高，对标时要留意。每行都标了来源和采集时间，可追溯。
- **成本口径（不要动）**：从 ERP 快照按「展示状态优先 → 有效未展示回退 → 排除作废」取单站最高；仓发优先含税单位成本、直发取采购价。成本结果直接复用旧表的「采用成本(元)」列，没有重算。
- **加价档（不要动）**：直发 2%/5%/8%，仓发 5%/12%/24%。输出价 = 成本 ×(1+加价比例)，四舍五入到分。京东价只作对标参考，**不参与**输出价计算。
- **同品背书**：用人工核实的「同款/不同规/相似」关系，替换旧的算法相似度候选。一对多时取主记录（同款优先 + 折算价非空 + 采集时间最新）。

## 7. 常见坑

1. **登录态丢失**：每次脚本都重新登录拿 cookie，不会过期；但账号密码要正确。
2. **别把导出接口混进来**：只要 URL 里出现 `mode=export_*` 就是扣积分的，本方案一律不用。
3. **历史数据别全字段存**：只留 5 个字段，否则文件过大、下游读取慢。
4. **一对多 SKU 取最新**：历史按时间倒序，去重取第一条；CSV 一对多取主记录时采集时间要做正确的时间倒序（用时间戳取负），否则会取到旧价——本次踩过这个坑，已修好。
5. **CSV 新价源是手动下载的**：定时任务在 CSV 缺失时会回退到历史价库。要连 CSV 也自动更新就得走导出、会碰积分，与「积分不能用」冲突，暂未接。
