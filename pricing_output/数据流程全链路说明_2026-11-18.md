> 这份文档讲的是**数据本身**：我们手上到底有哪几份数据、每份是什么、从哪来、字段什么意思、彼此什么关系、哪些口径是已经拍板不能改的，以及接下来该往哪走。
>
> 具体的操作步骤和接口细节，另有《天镜智价拉数交接说明》；这份是"读懂数据"用的，不是"照着跑"用的。
>
> 整理日期：2026-11-18

## 一、先看全景：一条链，四层数据

整件事可以浓缩成一句话：

> 以 **4940 个禄品商品**为基准，分别外接**成本**、**京东对标价**、**同品关系**三路数据，按拍板规则算出三档定价，再判断每个品要不要选、选哪一档。

数据从上游到下游分四层，**上一层的产出是下一层的输入**：

| 层级 | 这一层解决什么问题 | 主要数据 |
|---|---|---|
| ① 基准层 | "给哪些品定价" | 禄品 4940 筛选表 |
| ② 事实层 | "每个品的成本是多少、京东卖多少、和京东哪个品是同一个" | ERP 站点成本快照、京东 VOP / 历史比价表 / 天镜新价、天镜同品映射 |
| ③ 计算层 | "按规则算出三档价、并做同品背书" | 7 个脚本接力 |
| ④ 产出层 | "最终给人看、拿去做决定的表" | 完整版 → 含新京东价 → 含选品建议，外加同品关系主表 |

**一个最重要的认识**：这三路外接数据（成本 / 对标价 / 同品关系）**各自独立采集、各管一件事**，最后在"P 码"这个钥匙上拼到一起。理解了这个，就理解了整条链。

## 二、逐份数据拆解（重点）

下面按"数据身份"逐份拆。每份都按同一个框架讲：**它是什么 → 从哪来 → 有多少 → 关键字段 → 我怎么理解它 → 它在链里的角色 → 要注意什么**。

### 2.1 基准数据：禄品 4940 筛选表

| 项目 | 内容 |
|---|---|
| 它是什么 | 这次要定价的 4940 个禄品商品的名单，是整个链条的"骨架" |
| 从哪来 | 业务仓库 `01_源数据/禄品4940_筛选表_2026-11-09.xlsx`（本次本地工作区没有这份，脚本按仓库路径读取） |
| 有多少 | 4940 个 P 码，且已验证无重复 |
| 角色 | 所有后续数据都围着这 4940 个 P 码转；多出来的、对不上的，一律以它为准 |

**怎么理解它**：这是"题面"。所有成本、京东价、同品关系，本质都是去给这 4940 个 P 码各自"填空"。基准行数 4940 从头到尾没变过，是校验对不对的第一道尺子。

### 2.2 成本数据：ERP 站点成本快照

| 项目 | 内容 |
|---|---|
| 它是什么 | 每个禄品商品在**各个网站/站点**上的成本明细原始快照 |
| 从哪来 | 本来生活 ERP 只读接口 `ProLhotse/GetListByBasic`，一次性拉取，只 SELECT 不写库 |
| 有多少 | 57,592 条（一个商品可能对应多个站点，所以行数远大于 4940） |
| 文件 | `源数据_ERP站点成本_2026-11-13.jsonl`（23M） |
| 取数说明 | `取数说明.json`（记录了接口、批量、字段、状态枚举） |

**关键字段与含义**：

| 字段 | 含义 | 用途 |
|---|---|---|
| `ProductID` / `ProductBasicSysNo` | 商品标识，P 码的数字部分 | 和基准表 P 码对上（P 码去掉首字母） |
| `WebSiteSysNo` | 站点编号 | 同一商品在多个站点有不同成本，要"取单站最高" |
| `Status` | 状态：`1`=上架展示，`0`=有效未展示，`-1`=作废 | 决定取值优先级，作废全程排除 |
| `IsDelete` | 是否删除 | 删除的一律排除 |
| `UnitCost` | 含税单位成本 | 仓发商品优先取它 |
| `DefaultPurchasePrice` | 采购价 | 直发商品取它；仓发无含税成本时也取它 |
| `IsDirectSend` 等 | 发货方式标记 | 辅助判断直发 / 仓发 |

**我怎么理解它**：这份数据是"原材料"，不是成品。一个商品散落在多个站点、多个状态里，有展示的、有未展示的、有作废的。**成本口径的全部复杂性，就在于怎么从这一堆原始记录里"挑出那一个值"**——这个挑选规则见第三节。

**要注意什么**：这是整个链条里最关键、也最容易出错的一份。早期只取了 `Status=1`（展示状态），导致 1644 行成本缺失；后来才改成"展示优先、未展示回退"，补到 4897 行有成本。最终仍有 **43 个商品只有作废记录、确实无成本**，这是真实的数据缺口，不是 bug。

### 2.3 对标价数据：三路来源，一个优先级

京东对标价这件事，前后用了三路数据，现在**按固定优先级串起来用**。理解这三路的关系，是理解"京东价是怎么来的"的关键。

#### ① 新 CSV（天镜人工核实导出）—— 现在的主来源

| 项目 | 内容 |
|---|---|
| 它是什么 | 天镜智价上"人工核实过的同品关系 + 现场采集的京东售价"导出表 |
| 从哪来 | 天镜后台导出，`~/Downloads/verified_mapping_export_2026-11-16_...csv` |
| 有多少 | 40,684 行；其中和禄品 4940 交集 3105 个 P 码、可用折算价约 2807 个 |
| 关键字段 | 商品编码(P码)、京东SKU、关系类型、转化比例、**售价**、**售价（不同规计算折算后）**、到手价、店铺、采集时间 |

**我怎么理解它**：这是目前**质量最高**的对标价来源，因为它同时给了两样东西——"这两个品是不是同一个"的人工结论，以及"京东现在卖多少"的现场采集价。**用户明确拍板：对标价取"售价（不同规计算折算后）"这一列**，这样 500ml×2 和 500ml 之类的差异才能公平对比。

#### ② 天镜历史价库 —— 新 CSV 没有时的回退

| 项目 | 内容 |
|---|---|
| 它是什么 | 天镜智价上所有历史价格查询记录的本地快照 |
| 从哪来 | 免费查询接口 `get_history` 全量拉取（不消耗积分、不走要扣 204 积分的导出） |
| 有多少 | 409,336 条，时间跨度 2026-01-14 至 2026-11-16 |
| 文件 | `源数据_天镜价格历史全量_2026-11-17.jsonl`（49M） |
| 字段 | `skuId`、`jdPrice`、`salePrice`、`status`、`fetchTime`（已瘦身，只留必要字段） |

**我怎么理解它**：这是一个"京东价的历史档案库"。按 SKU 查时，**取最新一条**（文件按时间倒序，首次出现即最新）。它只在"新 CSV 没给这个品价格"时顶上。

#### ③ 历史比价表 1.29 —— 更早的兜底

| 项目 | 内容 |
|---|---|
| 它是什么 | 1 月 29 日的京东比价总表 |
| 文件 | `源数据_京东比价总表1.29.xlsx`（3.8M） |
| 角色 | 最初的对标价来源，现在只在更前面两路都没有时保留旧值 |

#### ④ 建议零售价 —— 最后一道兜底（非京东价）

| 项目 | 内容 |
|---|---|
| 它是什么 | 基准表里自带的"建议零售价(元)" |
| 角色 | 连上面三路都没有京东价时，拿它当对标价，**保证每行都有成本、有对标价** |
| 规模 | 约 1601 行走这条兜底 |

**要注意什么**：这 1601 行的"京东C端价"**其实不是真实京东价**，是建议零售价顶替的。表里已标注"建议零售价(兜底·非京东价)"，**这些行的空间率仅供参考**，不能当成真实渠道空间来谈判。

**对标价优先级一句话记住**：

> 新 CSV 折算价 → 天镜历史价库最新 → 旧表保留价 → 建议零售价兜底

### 2.4 同品关系数据：解决"两个 P 码其实是一个品"

这是整件事里最需要"人来判断"的一块，也是为什么要单独产出一份附件表的原因。

**为什么需要它**：禄品的 P 码和京东的 SKU 是两套编号，同一个实物两边编号不同、名字也有差异（比如 g / 克、ml、500ml×2 与 500ml）。不先确认"这俩是同一个品"，就敢拿京东价对标，是站不住脚的。

同品关系数据也经历了三代：

| 代际 | 数据/文件 | 做法 | 现状 |
|---|---|---|---|
| 第一代 | 历史比价表 1.29 | 人工标过"同品同规格=是"的，直接采信 | 并入主表 |
| 第二代 | `同品关系_候选相似度与人工确认_2026-11-16.xlsx` | 算法算相似度给候选 + 质疑点，交人工确认；**绝不自动判定同款** | 已被人工核实结果替换 |
| 第三代 | 天镜同品映射（40,684 条）+ 新 CSV | 天镜上人工核实的关系，含关系类型、转化比例 | **现在采信这一代** |

**天镜同品映射的字段**：

| 字段 | 含义 |
|---|---|
| `vop_sku` | 京东侧 SKU |
| `internal_code` | 内部 P 码 |
| `relation_type` | 关系类型：同款 / 不同规 / 相似 |
| `ratio` | 转化比例（不同规时用于价格折算） |
| `remark` / `created_at` / `updated_at` | 备注与时间戳 |

**关系类型的优先级**：`同款` > `不同规` > `相似`。一个 P 码有多条候选时，按这个顺序选主记录；**一对多（一个禄品找不到唯一对应的京东品）的候选一律不采信**，避免配错价。最终形成 **3302 条人工核实关系**的《同品关系_人工核实主表》。

**我怎么理解它**：它是"对标价凭什么这么配"的证据链。定价表里的"同品背书"那一列，就是这条关系的浓缩版；详细到每个候选的，全在附件主表里。关系为"相似"的，价格只作参考（表里已标注）。

## 三、关键定义：已经拍板、不能自行改的口径

这一节是"口径字典"。这些是业务红线，改任何一个都要用户本人确认。

### 3.1 成本取值定义

> **分两步走：先定状态层级，再定字段层级。**

**第一步：状态层级**（先去哪一层找）
1. 先在"上架展示"（`Status=1`）记录里取**单站最高值**；
2. 取不到，回退到"有效未展示"（`Status=0`）记录里取单站最高；
3. 作废（`-1`）和已删除记录**全程排除**。

**第二步：字段层级**（在这一层里取哪个字段）
- **仓发商品**：优先取**含税单位成本**（`UnitCost`）单站最高；没有含税成本，才取**采购价**（`DefaultPurchasePrice`）单站最高。
- **直发商品**：取**采购价**（`DefaultPurchasePrice`）单站最高。

每条结果都会写明"展示状态"还是"回退未展示"，方便核对。

### 3.2 加价档定义

| 发货类型 | 档①（低） | 档②（中） | 档③（高） |
|---|---|---|---|
| 直发 | 2% | 5% | 8% |
| 仓发 | 5% | 12% | 24% |

输出价 = 采用成本 ×（1 + 加价比例），纯成本加成。**京东价只作对标，不参与定价计算。**

### 3.3 京东价优先级定义

新 CSV 折算价 → 天镜历史价库最新 → 旧表保留价 → 建议零售价兜底。每行标注来源与时间。

### 3.4 选品与空间率定义

- **空间率** =（京东价 − 输出价）/ 京东价。含义：留给下游渠道的利润空间。
- **背景**：定价后不做直客，必须给渠道留空间，所以空间率是选品的核心依据。
- **选品规则**：最低档（档①）空间率 ≥ 10% → 选中；< 10% 或倒挂 → 不选；无成本 → 不选。
- **选档规则**：在选中的品里，**从最高档往下找第一个仍满足空间率 ≥ 10% 的档**，在守住渠道空间的前提下尽量多留利润。
- 空间下限 10% 是用户采纳的建议值。

## 四、数据怎么被加工：7 个脚本的接力

| 步骤 | 脚本 | 读什么 | 产出什么 |
|---|---|---|---|
| 1 | `pull_erp_site_costs.py` | 基准 4940 P 码 + ERP 只读接口 | ERP 站点成本快照（57,592 条） |
| 2 | `build_rule_pricing.py` | 基准表 + VOP + 历史比价表 + ERP 快照 | 规则定价_成本与京东比价 2026-11-13 |
| 3 | `build_similarity.py` | 基准表 + 历史比价表 + VOP + 上一步 | 同品关系_候选相似度与人工确认 |
| 4 | `build_final_pricing.py` | 基准 + ERP 快照 + 上两步 + 历史比价表 | **完整版**（原始数据+规则+结果三合一） |
| 5 | `fetch_tianjing_free.py` | 天镜免费接口 | 天镜历史价库 + 同品映射 + 取数日志 |
| 6 | `rebuild_pricing_new_price.py` | 完整版 + 新 CSV + 天镜两份快照 | **含新京东价** + 同品关系主表 |
| 7 | `add_selection_advice.py` | 含新京东价 | **含选品建议**（最终成品） |

**接力的关键**：每一步都**只读上游、另存新文件**，不改动源文件。所以任意一步出问题，都能从上一步重跑，不会污染原始数据。步骤 6、7 是每天定时自动跑的（拉数 → 重建 → 加选品建议）。

**顺序不能颠倒**：必须先算出"含新京东价"，才能在它基础上加选品建议；否则最终成品和产出物会对不上。

## 六、引导方向：现在怎么看、以后怎么走

### 6.1 现在该用哪份

- **拿去做决定、对外沟通**：只发《含选品建议》这一份，它是最终成品。
- **被问到对标价依据**：翻《同品关系_人工核实主表》。
- **《含新京东价》和《完整版》**：留作排查和追溯，不用外发。

### 6.2 最终成品的关键数字（截至 2026-11-17）

| 指标 | 数值 |
|---|---|
| 基准行数 | 4940 |
| 有成本 | 4897（43 个仅作废记录，真实缺口） |
| 有对标价 | 4940（其中约 1601 行为建议零售价兜底，并非真实京东价） |
| 选中 / 不选 | 4163 / 777 |
| 建议档位 | 档3：3806，档2：231，档1：126 |
| 公式校验 | 输出价公式 14,691 格，零错误 |

### 6.3 三个要打问号的地方（用之前心里有数）

1. **约 1601 行的"京东价"是建议零售价兜底**，不是真实京东价。这些行的空间率只是"看起来有空间"，别拿去当真实渠道利润谈判。若要严谨，需补这批品的真实京东价。
2. **关系为"相似"的品**，价格仅作参考（已标注），不建议直接采信其对标价。
3. **43 个仅作废记录的商品无成本、不出价**，是真实数据缺口；若要覆盖，得重新取数或人工补成本。

### 6.4 往后的方向建议

- **近期**：把 1601 行兜底价补成真实京东价，是提升整表可信度的第一优先级——它直接影响空间率和选品结论的可靠性。
- **机制上**：天镜新 CSV 的对标价和人工核实关系质量最高，应尽量提高它对 4940 品的覆盖率，减少对历史价库和建议零售价的依赖。
- **自动化**：拉数→重建→选品建议已设为每天定时跑，产出物会随新数据滚动更新；每次跑完核对 stdout 的四个数（基准 4940 / 有对标价 4940 / 有成本 4897 / 公式错误 0）。
- **口径护栏**：成本、加价档、价格优先级、选品规则都属于拍板口径，任何调整都需要你本人确认后再改脚本重算，不要就地改表。
